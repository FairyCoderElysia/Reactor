## Summary

《反应堆》的整个玩法成立与否，取决于"把跑通的组合**封装**成可再次调用的实体"这一步（`design/game-brief.md` 自述这是全游戏最不确定的一步）。本 ADR 把 `design/composition-model.md` 的设计意图固化成**模拟内核必须实现的四条架构约束**：层级递归有下界无上界、封装必须同时产出"可见实体 + 可调用符号"、递归必须过三道闸（基例 / 环检测 / 深度上限）、授权面分种植层与整理层。这四条决定数据结构、递归终止条件与内核安全边界，因此在写第一行内核代码之前定下来。

## Context

### Problem Statement

《反应堆》的核心许诺是**玩家把规则封成部件、把部件封成工厂，一层层往上调用**。
这个许诺要求模拟内核支持**任意深度的递归组合**，而递归组合天然带来两个致命失败模式：

1. **环** —— 玩家定义"A 调用 B、B 又调用 A"。结算时它会永远跑不完。
2. **深不可测的嵌套** —— 即使无环，深度也可轻易失控，导致栈溢出或单帧爆炸。

这两种失败都必须被**内核**接住，而不是靠玩家自律。不做这个决定、或者把它推到"以后再管"的代价是：等规则在代码里散开之后再补闸，等于重写结算循环 —— 而结算循环是一切的地基。

### Current State

**尚不存在**。代码根 `Source/Reactor/` 只有 UE 模块骨架
（`Reactor.Build.cs`、`Reactor.cpp`、`Reactor.h`、两个 Target.cs），没有任何模拟代码。
设计意图写在 `design/composition-model.md`（63 行）与 `design/game-brief.md`。
本 ADR 是第一次把那些意图变成有约束力的技术合同。

### Constraints

- **引擎**：UE 5.8.3，C++ 为主。逐格模拟必须走 C++ —— handoff 实测口径：256×256 = 65,536 格、60fps 下约 390 万次更新/秒；512×512 约 1570 万次/秒。这是选 UE 的直接理由（用户 C++ 最熟，且该量级在 C++ 里是免费的）。
- **数据驱动是硬性架构约定**（handoff 已定）：规则表、物质反应表、参数全放数据文件 / 蓝图可编辑变量，**调规则不重编译**。本 ADR 的三道闸因此也必须参数化，不能把"深度上限"硬编码成常量。
- **平台**：PC / 单机 / 2D。没有联网，所以**不需要考虑确定性重放的网络同步** —— 但仍建议保持结算确定（见"后果"）。
- **原型期不做编辑器 UI**：规则直接写在数据文件里（brief 的 Out of scope）。这不改变三道闸的归属 —— 闸在内核。
- **存疑**：目标网格规模与性能预算尚未确定（`project.yaml` 的 `performance` 留空是刻意的）。

### Requirements

- **功能 1**：递归必须能终止，且终止点是**基础物质**（游戏固定提供、不可再拆）。
- **功能 2**：封装一次必须**同时**产出「世界里可见的实体」与「上一层可调用的符号」，缺一则玩法幻想不成立。
- **功能 3**：封装那一刻必须检测有向图成环并**拒绝**，且拒绝要给出可读的错因（玩家要知道是哪条规则害的）。
- **功能 4**：即使无环，嵌套深度也必须有硬上限；超限报可读的错，**不崩**。
- **功能 5**：三道闸的阈值必须**参数化**（数据驱动约定），不是编译期常量。
- **性能 1**：闸的检查发生在**封装时**（一次性），不在每帧结算的热路径上重复全图检查。
- **可证性 1**：三道闸必须能在无引擎依赖的单元测试里被验证。
- **可扩展 1**：授权面分两层（种植层 = 可视化拖拽；整理层 = 类语言写法）。原型阶段两层都不做，但内核的数据模型必须**同时容得下**两层，否则将来要重写。

## Decision

### 一、层级栈：有下界，无上界

```
完整系统        ← 由多个子系统互相调用、依赖、组合而成
  ↑ 封装
子系统          ← 里面还有子系统的子系统……可以一直往下拆
  ↑ 封装
部件 / 工厂     ← 基础物质 + 规则造出来的"具体东西"
  ↑ 规则（玩家定义）
基础物质        ← 游戏提供，固定          ← 递归基例
```

**性质：没有上界，但有下界。** 一路往下拆永远能拆到基础物质 —— 那就是递归的基例。

### 二、封装的产出是**一对**，不是两个功能

每次封装必须同时给玩家两样，缺一个幻想就塌：

1. **一个可见的实体** —— 在世界里存在、能被看见、能被指着说"这是我造的"
2. **一个可调用的符号** —— 在上一层里，能像基础物质一样被规则引用

> 第 1 条是为什么"涌现可视化"是**核心反馈**而不是打磨项。
> 第 2 条是为什么语言层（整理层）最终会自己长出来。

**架构含义（本 ADR 的核心增量）**：这一对必须由**同一次封装操作原子地产出**，且两者
共享同一个标识。若实现成"先造实体、以后再注册符号"，就会出现实体与符号不一致的中间态，
而玩家的每一次封装都会经过这个中间态。因此接口必须一次返回两者。

### 三、递归的三道闸

| 闸 | 作用 | 实现归属 |
|---|---|---|
| **基例** | 基础物质不可再拆 —— 递归的天然终点 | 数据模型（物质表的 `bIsPrimitive` 一类标记） |
| **环检测** | 玩家造的"互相调用"是一张有向图，**可以成环**（A 调 B、B 又调 A）。封装那一刻必须检测并拒绝成环 | 封装操作的提交路径 |
| **深度上限** | 即使无环，嵌套深度也要有硬上限；超限时报可读的错，而不是崩 | 封装操作的提交路径 + 结算循环的防御性检查 |

**这三道闸属于 MVP，不是打磨项。** 一个环就足以让结算循环永远跑不完 ——
在玩家眼里就是"游戏卡死了"，而不是"我犯了个错"。

### 四、授权面分两层

| 层 | 形式 | 职责 |
|---|---|---|
| **种植层** | 可视化（拖拽 / 摆放） | 门槛低：做出东西、发现模式、"试试这个会怎样" |
| **整理层** | 类高级语言的写法 | 层次一深画布就变意大利面；调用 / 嵌套 / 递归是语言的天生强项 |

**升级规则：亲手探索出来的东西，一旦封装命名，就成为语言里的一个词。**
抽象阶梯每爬升一层，工作台就从"手"换成"语言"。

（原型阶段两层都不做 —— 规则直接写在数据文件里。见 brief 的 Out of scope。）

### 五、可视化是核心反馈回路，不是打磨项

Noita 的合成爽感其实来自**打出去** —— 即时反馈由战斗提供。
**本作没有战斗，合成就是全部玩法。** 所以反馈只能来自"看着它跑"本身：

> 没有"看得见它在跑" + **"看得见是哪条规则在起作用"**，整个循环就闭合不了 ——
> 玩家做完一个东西，不知道它有没有用、为什么有用，就不会有下一次。

**架构含义（本 ADR 的核心增量）**：结算发生时必须**留下可归因的痕迹**（哪条规则在
哪个格子上做了什么）。这不是渲染层的事后加装 —— 如果内核不产出归因信息，渲染层
无从"看见是哪条规则干的"，而这正是失败反馈的唯一来源（brief 的"失败会留下可读的现场"）。

### Key Interfaces

> 以下为**形状约定**，不是最终签名。符号名按 `naming` 约定（PascalCase、
> 结构体 `F` 前缀、类 `U`/`A` 前缀）。原型期规则写在数据文件里，所以这些接口
> 首先由**数据 schema** 承载，C++ 类型随后。

```
// 闸① 基例：物质表里标出不可再拆的那些
struct FSubstanceDef
{
    FName  Id;
    bool   bIsPrimitive;   // true = 递归基例，不可再拆
    // ...反应表条目
};

// 组合节点：递归的一层。含子调用即意味着这是有向图的一个节点
struct FCompositionNode
{
    FName                Id;
    TArray<FName>        CalledNodeIds;   // 出边 —— 环检测的输入
    // ...规则 / 参数
};

// 闸② / 闸③ 的唯一入口
// 返回：成功时【同时】给出实体与符号；失败时给出可读错因
struct FSealResult
{
    bool             bSealed;
    FSealFailure     Failure;     // 指明是哪条规则 / 哪条边成的环，或深度超限
    // 成功时二者同时有效，共享同一 Id：
    //   FSealedEntityRef  VisibleEntity;   ← 世界里的可见实体
    //   FName             CallableSymbol;  ← 上一层可引用的符号
};

FSealResult SealComposition(
    const FCompositionGraph& Graph,     // 候选图
    const FSealLimits&       Limits      // 数据驱动：深度上限等，非常量
);

// 归因记录：可视化层的输入。内核不产它，"看见是哪条规则干的"就无法实现
struct FAttributionRecord
{
    FIntPoint  Cell;
    FName      RuleId;
    // ...发生了什么（反应 / 无反应 / 被闸拦下）
};
```

### Implementation Guidelines

1. **闸只在封装提交路径上跑全图检查，不在每帧结算的热路径上跑。** 结算循环只做廉价的**防御性**深度检查（防止闸被绕过），不做全图环遍历 —— 否则每次结算都会带上一个 O(V+E) 的开销，在 65k 格规模下不可接受。
2. **提交路径必须只有一条。** 种植层与整理层**都**只能经由它封装。两条路径意味着两套校验逻辑，早晚分叉，而分叉出来的那条就是漏洞。
3. **拒绝必须是可读的。** 环检测失败时，错因要能指出**构成环的那条边**（或至少那条规则），因为 brief 明确要求"失败会留下可读的现场"。一个只有 `false` 的返回值不满足这条。
4. **阈值参数化。** 深度上限、是否允许自引用等，走数据驱动约定（数据文件 / 蓝图可编辑变量），不写成编译期常量 —— handoff 已把"调规则不重编译"定为架构约定。
5. **归因记录是内核职责，不是渲染职责。** 内核必须产出它；渲染层只消费。反过来做（渲染层反推是哪条规则）不可行，因为格子状态是叠加的结果。
6. **保持结算确定性。** 单机不需要网络同步，但确定性能让"同一份谜题文件重跑得到同一结果"成立 —— 而 brief 把谜题存成**版本化 + 自包含**的文件格式列为第一天就要遵守的硬约束。归因记录也因此可复现。
7. **不要在闸里做 GC 敏感操作。** 三道闸是纯数据校验，不持有 UObject 引用。

## Alternatives Considered

### Alternative 1: 只在结算时检测环（运行时防护，不做封装时校验）

- **Description**：封装时不检查，允许玩家造出环；结算循环加步数上限，跑超了就算这一局失败。
- **Pros**：实现最省；"环导致递归爆掉"可以直接当作一种失败玩法（brief 的失败清单里确实有"规则成环导致递归爆掉"）。
- **Cons**：设计文档明确反对。玩家看到的会是"游戏卡死了"而不是"我犯了个错" —— 失败必须留下**可读的**现场，而超步数上限本身不说明是哪条规则害的。更糟的是：如果环不总是立刻爆（取决于触发条件），它会变成一个潜伏的随机卡死。
- **Estimated Effort**：低。
- **Rejection Reason**：与 brief 的失败设计原则直接冲突（"失败会留下可读的现场"）。但**保留其中合理的一半**：结算循环**仍然**要有防御性的深度/步数上限，作为闸被绕过时的兜底 —— 见 Implementation Guideline 1。两者不是二选一。

### Alternative 2: 深度上限用编译期常量

- **Description**：`constexpr int32 MaxDepth = N;`，改上限要重编译。
- **Pros**：最简单、最快、编译器可优化。
- **Cons**：违反 handoff 已定的数据驱动架构约定 —— 那个约定的全部意义就是"调规则不重编译，把 UE 的迭代税压到接近零"。深度上限恰好是原型期最需要反复试的参数之一（设计文档说这个数值要通过手感确定）。
- **Estimated Effort**：低。
- **Rejection Reason**：与硬性架构约定冲突。上限本身是 MVP 参数，而参数必须可调。

### Alternative 3: 用 `TInstancedStruct` 表示组合节点的异构载荷

- **Description**：UE 的 `TInstancedStruct` 可以在一个属性里装任意结构体，很贴合"一个节点可以是物质、规则、或已封装的部件"这种异构性。5.8 正好为它加了 `*` / `->` 运算符便利。
- **Pros**：省掉一层手写的 variant 分派；编辑器内建可编辑性（对将来"整理层/编辑器"友好）。
- **Cons**：它是**引擎特性**，会把闸的校验逻辑和 UE 的反射/序列化绑在一起 —— 而三道闸恰恰是本 ADR 里最值得**脱离引擎单独验证**的部分（见 Engine Compatibility 的 Knowledge Risk 讨论）。此外它把一个纯数据校验问题变成了 GBuffer-无关但反射相关的问题。
- **Estimated Effort**：中。
- **Rejection Reason**：**暂不采用，但不是否决。** 原型期用朴素数据结构把闸验证清楚（可脱引擎测试），等"整理层/编辑器"真正开工、异构性开始带来实际痛感时再评估。若那时采用，应另开 ADR 记录，并注明它只影响表示层、不影响闸的语义。

## Consequences

### Positive

- 三道闸在第 1 步就存在，玩家遇到的失败是**可读的**，而不是卡死。
- 封装的"双产出"被固化成**原子操作 + 共享标识**，消除了实体与符号不一致的中间态。
- 归因记录被定为内核职责，因此"看得见是哪条规则在起作用"成为可实现的需求，而不是渲染层的一次希望。
- 三道闸与引擎解耦，可先在纯 C++ 测试里验证 —— 不必等 UE 工程就位，也不受 5.8 未知 API 影响。

### Negative

- **"无上界"是产品许诺，"有硬上限"是工程事实 —— 二者必须被诚实地调和。** 设计文档说本作与 Noita 的关键差别是"允许递归与层层封装，没有固定上界"。工程上深度上限必须存在。这对幻想有真实风险：玩家撞到上限时会觉得被骗。**缓解**：上限要足够高以至于正常玩法碰不到，且超限错误必须可读并解释"为什么"（而不是静默失败）。这个数值需要原型手感确定，本 ADR 不预设。
- 封装提交路径被强制单一化，意味着种植层与整理层不能各自优化自己的提交体验 —— 将来若两层的交互范式冲突，会在这里产生摩擦。
- 环检测发生在封装时，所以玩家会在"提交那一刻"被拒绝，而不是在"看它跑的时候"发现 —— 对纯粹的沙盒试验心态来说，这一刻的打断感需要被设计好。

### Neutral

- `design/composition-model.md` 保留原地，不删除。它是**面向设计的**表述（含"为什么这么设计"的语气与插图式层级栈），本 ADR 是**面向实现的**合同。两者服务不同读者：前者给人看，后者给故事与评审看。若日后二者冲突，**以本 ADR 为准**，并更新设计文档。
- 三道闸的参数化值尚未确定，因此本 ADR 不包含具体数字。这不影响它可以被 `Accepted` —— 约束是"必须参数化"，不是"必须等于某个数"。

## Risks

| Risk | Probability | Impact | Mitigation |
|------|------------|--------|-----------|
| 深度上限的数值定得太低，破坏"无上界"的产品许诺 | 中 | 高（玩家体感被欺骗） | 上限参数化 + 通过原型手感定值；超限错误必须解释原因。见 Consequences 的 Negative |
| 环检测实现漏检（如多跳环、自引用） | 中 | 高（模拟挂死） | 环检测必须有独立单元测试，覆盖自引用 / 两跳 / 长环；结算循环保留防御性深度上限作兜底 |
| 提交路径被分裂成两条（种植层 + 整理层各一条） | 中 | 中 | Implementation Guideline 2 明确单一入口；评审时检查是否有第二个封装入口 |
| 归因记录被当成"以后再加" | 中 | 高 | 本 ADR 把它定为内核职责；若内核不产它，可视化这条核心反馈回路无法实现 —— 而 brief 说循环不闭合就没有下一次 |
| 逐格结算在目标规模下达不到 60fps | 低 | 中 | handoff 的测算支持 C++ 可做（256×256 约 390 万次更新/秒）。真正的风险是热路径上误加了闸的全图检查 —— Guideline 1 已封堵 |

## Migration Plan

尚无可迁移的代码 —— 代码根只有模块骨架，无模拟代码。本 ADR 因此不是"迁移"，而是
**第 1 步开工时必须满足的前置条件**。

1. **在写结算循环之前**，先用可脱引擎测试的结构把三道闸实现出来（基例 / 环检测 / 深度上限），并用 Automation Spec 覆盖：自引用、两跳环、长环、恰好等于上限、超出上限。
2. **归因记录的数据结构先于渲染层落地。** 可视化层消费它；若等渲染层开工才想起它，就得回头改内核。
3. **封装的"双产出"在一次操作内完成**，共享标识；先写测试证明失败时不留半成品。
4. **参数化接入数据文件 / 蓝图可编辑变量**，验证"改上限不重编译"确实成立。

**Rollback plan**：本 ADR 若被证明错误（例如"无上界"的产品许诺实际上必须放弃），
回滚点是"把三道闸从硬约束降级为玩法机制"。但请注意：**环检测无法回滚掉** ——
没有它，结算循环会被玩家输入挂死，这是工程必然性而非设计选择。可回滚的只有
"上限的具体形态与拒绝方式"。

## Validation Criteria

- [ ] 自引用环（A 调 A）在封装时被拒绝，且错因指出该规则
- [ ] 两跳环（A 调 B、B 调 A）在封装时被拒绝，且错因指出构成环的边
- [ ] 长环（≥ 3 跳）同样被拒绝 —— 证明检测不是只看直接边
- [ ] 合法深度的嵌套（恰好等于配置上限）**通过**
- [ ] 超过配置上限的嵌套被拒绝，且报错可读、不崩
- [ ] 改动深度上限的参数后**不需要重新编译**
- [ ] 封装失败时**不留下半成品**（无孤立实体、无孤立符号）
- [ ] 封装成功时实体与符号共享标识，二者同时可用
- [ ] 结算循环含防御性深度检查，且**未**在热路径做全图遍历
- [ ] 归因记录足以回答"这个格子这一步是哪条规则干的"
- [ ] 同一份输入重跑两次，结算结果与归因记录**完全一致**（确定性）
