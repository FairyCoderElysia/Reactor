**Epic**: `settlement-core`（Build order 第 1 步）
**Status**: Ready
**Estimate**: 3–5 天（`coarse`）

## 为什么先做这个

`design/game-brief.md` 的 Build order 第 1 步是「结算引擎 + 最小空间（3 种物质、3 条规则）
+ 最粗糙的可视化」，目的是**先确认"看着它自己反应"本身有快感**。

但在确认快感之前，有个前提必须先成立：**规则必须能在不重新编译的前提下改动。**
这是 `production/handoff-2026-10-05.md` 定下的硬性架构约定 —— UE 的编译很贵，
而本作的核心玩法就是反复调规则。如果调一条规则要等一次 C++ 重编译，
迭代成本会直接杀死原型阶段。

所以本故事做两件事，且**顺序不能反**：先把数据加载与网格打通，再让结算循环跑起来。

## 交付物

### 1. 数据文件（`Content/` 或 `Config/` 下）

三张表，**全部在运行时加载，改动不需要重编译**：

| 表 | 内容 | 初始规模 |
|---|---|---|
| 物质表 | 每种物质的 id、显示名、颜色、`bIsPrimitive` 标记 | 3 种 |
| 反应表 | 两两相遇产生什么（A+B → C） | 覆盖 3 种物质的两两组合 |
| 规则表 | 条件 + 效果，可调参数 | 3 条 |

`bIsPrimitive` 是 `composition-model.md` 里**递归基例**的落点 —— 即使本故事还用不到递归，
这个字段必须现在就存在，否则后来加递归时要改数据格式与所有已存文件。

### 2. 网格数据结构

- 基准 `256×256` = 65,536 格（handoff 的测算基准）
- 必须能扩到 `512×512`（26 万格）而**不改代码** —— 尺寸是数据/配置项，不是常量
- 每格至少存：物质 id、以及一个"本步是否被改动"的标记

### 3. 结算循环

- 每 tick 遍历全部格子，按反应表与规则表结算
- **双缓冲**（读上一帧的状态、写下一帧的状态），否则结算顺序会污染结果
- 固定步长，不依赖帧率
- **确定性**：同一份输入跑两次，结果必须逐格一致

## Acceptance Criteria

1. 三张数据表的字段与加载路径确定，格式写进 `docs/`
2. 改一条规则或一条反应，**不重新编译**即生效（需实测：改 → 跑 → 看到差异）
3. 网格基准 `256×256` 可创建，且**扩大或缩小只需改配置**，不改代码
4. 结算循环以固定步长前进，不随帧率漂移
5. 同一次运行内连续两 tick 的差异可观察（东西确实在变）
6. **确定性**：同一初始状态跑两次得到逐格相同的结果（自动化测试）
7. `Automation Spec` 测试存在且通过，命名以 `Reactor.` 开头（`commands.test` 按此过滤）
8. `commands.build` 能编译通过（**注意**：该命令此前未被验证，见下方风险）
9. **产出第一个真实的性能数字**：基准网格下每 tick 耗时实测值，填入 `project.yaml` 的 `performance.*`（此前刻意留空）

## 验证方式

- 单元测试：`Automation Spec`，覆盖"同输入两次结果一致"
- 人工：改一条反应表的数值 → 不重编译 → 跑起来看到行为变化
- 性能：在基准网格下测 tick 耗时，记录数字（**这正是 `performance` 预算一直留空的原因 —— 现在有真数据了**）

## 风险与注意

- ⚠️ **`commands.build` 尚未验证过。** 原因：UE 5.8 的 UBT 需要 .NET 10（系统只有 6–9），
  且需要 `%LOCALAPPDATA%\UnrealBuildTool\` 可写。引擎自带 SDK 在
  `Engine/Binaries/ThirdParty/DotNet/10.0/win-x64`。**第一次跑这条命令时可能要先解决这个。**
- ⚠️ **headless 启动必须带 `-DDC-ForceMemoryCache`**，否则启动即 EXIT=3。已在 `commands.smoke` / `commands.test` 里。
- 不要把闸的检查放进结算热路径 —— 那是 story-003 的事，且属封装提交路径。
